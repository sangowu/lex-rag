# RetrievalStrategy 重构的回归验证

对应 `docs/agentic_loop_upgrade.md` 第 2.2 节的硬门禁。

改造内容：五个检索开关（mode / HyDE / multi-query / parent 展开 / rerank）从
`RAGPipeline.__init__` 的构造期配置，搬到 `_query_impl(strategy=...)` 的运行期参数。
`strategy=None` 时由 `RetrievalStrategy.from_config()` 构造默认策略。

配置：`chunks` 表 / hybrid / reranker on（rerank_top_k=60）/ chunk=1000, overlap=100 /
1000 条 CUAD QA。三次运行的配置完全相同。

## 结论：通过，但判定口径需要修正

第一次比对（基线 vs 改造后）出现 ±0.004 的差异，按规格字面要求的"每一个指标必须
完全一致"是不通过的。

于是**用同一份代码再跑了一次**做判别。结果是决定性的：改造后的两次运行之间同样
差 ±0.004，而第三次运行反而与改造前的基线在 hit@1 / hit@5 / hit@10 / mrr@5 /
p@5 上**完全相同**。

也就是说：**这 ±0.004（1000 条里约 4 条）的抖动独立于本次重构存在**，重构不是它的
来源。若不做第三次运行，就会把环境噪声误判成重构缺陷，然后去改一段本来正确的代码。

### 抖动来自哪里

两个来源，都不在本项目代码内：

1. **reranker 是远程模型**（SiliconFlow `bge-reranker-v2-m3`）。服务端不保证逐位
   可复现，排序边界上的样本会来回翻。
2. **Postgres 对分数相同的行不保证返回顺序**。Python 的 `sorted` 是稳定排序，会把
   数据库给出的顺序原样带到最终结果里。

两者都只影响**排序边界**上的少数样本，所以 hit@10 与 mrr@5 一动不动——名次差一位
不会改变"前 10 里有没有"，也几乎不改变倒数排名的均值。这个形态与"系统性 bug 会
单向偏移并带动相邻指标"正好相反，是判定为噪声的旁证。

### 修正后的判定口径

原口径（"完全一致"）在依赖远程模型的链路上不可达。后续回归以此为准：

- `hit@10` 与 `mrr@5` **必须完全一致**（对边界抖动不敏感，一旦变化即为真实回归）
- `hit@1` / `hit@5` / `recall@5` 允许 **|Δ| ≤ 0.005**（实测噪声上界）
- **不允许出现单向偏移**：若多个指标同时朝同一方向移动，即使幅度在阈值内也需追查
- 判定存疑时，**用同一份代码重跑一次**再下结论——这次就是靠它避免了误判

## 单元测试

新增 `tests/test_strategy.py` 14 个用例，覆盖与改造前的行为等价性：

- `from_config` 的默认取值复刻改造前（含 `fetch_k = rerank_top_k if rerank else top_k`
  这条容易漏掉的语义）
- 显式传 `k` 时的覆盖规则：开 rerank 只动 `top_k`，不开时 `fetch_k` 要一起动
- BM25 模式完全跳过 embedding
- HyDE 只作用于 hybrid 的向量那一路，BM25 仍用原文
- 重写后的查询用于检索，但 **rerank 始终用原问题打分**
- `expand_parent` 在 standard 表上被忽略
- `key()` 对不同策略不同、对相同策略稳定（防重复的基础）

全量 73 passed。

## 遗留缺口

`data/runs/eval/*.json` 只存聚合指标，没有逐条记录，所以无法直接看出是哪 4 条翻转、
分数差多少——这次只能靠重跑来判别。规格 2.5 节要求每轮落盘 chunk_id 与分数，检索层
评测也应补上，届时这类判别可以直接 diff，不必再花 27 分钟重跑一次。
